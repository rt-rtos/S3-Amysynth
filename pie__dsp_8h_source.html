1// ESP32-S3 PIE (128-bit SIMD) kernels for the AMY render path.
2//
3// Scope note - why this component is only a block memset and a block memcpy:
4//
5// The S3's PIE unit multiplies/multiply-accumulates on 8- and 16-bit lanes only
6// (EE.VMULAS.S16 -> 40-bit QACC/ACCX). 32-bit lanes get add/sub/shift/min/max/compare
7// and nothing else; there is no gather and no float SIMD. AMY's fixed-point build uses
8// SAMPLE = s8.23 = int32, so its hot-path multiplies (MUL8_SS, SMULR6, top16SMUL) are
9// 32x32 products that PIE cannot vectorize at all.
10//
11// That leaves the multiply-free, dependency-free, contiguous operations. The rest of
12// AMY's render path is either gather-indexed (the LUT oscillators walk a wavetable by
13// phase accumulator) or recurrence-bound (biquads, EQ, echo/chorus/reverb all carry IIR
14// feedback state), and neither is vectorizable on any SIMD unit. esp-dsp independently
15// agrees: its own ESP32-S3 biquad (dsps_biquad_f32_aes3.S) contains zero PIE
16// instructions.
17//
18// An earlier revision also vectorized AMY's scan_max() and block_norm(), which are
19// multiply-free reductions and so looked eligible. On-target A/B said otherwise: they
20// bought nothing on any scene and cost up to ~1% on filter-heavy ones. Nearly every
21// call is on a tiny buffer - scan_max(w, 4), scan_max(w, 6) for LPF24, and scan_max /
22// block_norm over the 8-entry filter_delay - where the vector setup costs more than the
23// scalar loop it replaces, and those buffers live inside synthinfo so they are not
24// aligned either. Multiply-free turns out to be necessary but not sufficient: the
25// operation also has to be long enough to amortise the vector setup, and in AMY only
26// the bulk block clears and copies are.
27//
28// Off the S3, every entry point falls back to libc memset/memcpy so AMY still builds
29// for desktop and other targets.
